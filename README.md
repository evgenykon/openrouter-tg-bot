# OpenRouter TG Bot — LLM bot в tg-чате

Telegram-бот, который добавляется в группу и отвечает только по тегу
`@<bot> <запрос>`. Контекст — история чата (ограниченная токен-бюджетом
модели). Работает только для пользователей из конфига. Сгенерированные
ответы — через OpenRouter.

## Как это работает

- **Тег, а не автоответ**: бот отвечает только когда его упомянули
  (`@bot что скажешь?`). Обычные сообщения сохраняются в историю, но
  игнорируются.
- **Доступ**: любой запрос/команда от юзера не из `allowedUserIds` получает
  «Service not available for you» — без вызова OpenRouter и без записи в базу.
- **Контекст**: история чата от новых к старым в рамках токен-бюджета
  (окно модели − `maxTokens` − системный промпт − резерв 30%).
  В историю попадают и сообщения пользователей, и обращения к боту (тег),
  и ответы бота. Каждое сообщение помечается именем автора, поэтому бот
  понимает, кто спрашивает и на чью реплику отвечает (в т.ч. через reply).
- **Личка**: бот отвечает на все сообщения, контекст — только сообщения
  этого пользователя.
- **Профиль**: у каждого разрешённого юзера есть текстовый профиль (Redis),
  которым он управляет сам. Профиль подкладывается в контекст и в групповом
  чате, и в личке — модель использует его для анализа. Профили подставляются
  безусловно (не обрезаются токен-бюджетом); при тесноте урезается только
  история чата, а профиль сжимается лишь по символам (`contextMessageMaxChars`).

## Настройка

1. **BotFather**: создай бота, затем обязательно
   `/setprivacy` → **Disable** (иначе бот не увидит обычные сообщения группы).
2. Добавь бота в группу.
3. Конфиги из шаблонов:
   ```sh
   cp .env.example .env
   cp config.example.json config.json
   ```
   - `.env`: `BOT_TOKEN`, `OPENROUTER_API_KEY`
   - `config.json`: `model`, `allowedUserIds` (telegram id юзеров),
     `systemPrompt`, `privateSystemPrompt`, `maxContextMessages`,
     `fallbackContextTokens`, `safetyMarginPercent`, `maxTokens`,
     `contextMessageMaxChars`
4. Запуск:
   ```sh
   docker compose up -d --build
   ```
   Redis поднимается автоматически с AOF-персистентностью
   (данные — в `./data/redis`, история — в Redis, переживает перезапуски).

## Команды

| Команда | Действие |
| --- | --- |
| `@bot <текст>` | запрос к модели (промпт — текст после тега) |
| `/start` | приветствие и начало диалога |
| `/profile` | показать профиль; `/profile set <текст>` — сохранить; `/profile add <текст>` — дополнить; `/profile clear` — очистить |
| `/compress_chat` | список групповых чатов, где ты есть; `/compress_chat <id>` — сжать историю чата в сводку |
| `/reset` | очистить историю чата (в личке — историю лички) |
| `/show_prompt` | показать текущий системный промпт |
| `/help` | список команд |

Команды видны в подсказке, когда начинаешь писать `@bot` в группе, и в меню.

## Деплой через GitHub Actions

Push в ветку `main` автоматически запускает `.github/workflows/deploy.yml`:
исходники заливаются на сервер **по SSH через `rsync`**, затем выполняется
`docker compose up -d --build`. Git на сервере не обязателен. Репозиторий
может быть приватным — серверу не нужен доступ к GitHub.

Файлы `config.json`, `.env` и `data/` в git не хранятся — они остаются только
на сервере. При rsync они исключены из передачи и защищены от удаления
(`--delete` + `--exclude`, без `--delete-excluded`), поэтому при деплое
не перезаписываются и не удаляются.

Работает с GitHub Environments. Job объявляет `environment: prod`, поэтому
переменные берутся из Environments → `prod` → **Variables**, а ключ —
из Environments → `prod` → **Secrets**.

**Environments → `prod` → Variables:**

| Variable | Значение |
| --- | --- |
| `DEPLOY_HOST` | IP/хост сервера (`23.227.194.192`) |
| `DEPLOY_USER` | SSH-пользователь (`deployer`) |
| `DEPLOY_TARGET` | путь к проекту на сервере (по умолчанию `/app/openrouter-tg-bot`) |
| `DEPLOY_PORT` | опционально, порт SSH (по умолчанию `22`) |

**Environments → `prod` → Secrets:**

| Secret | Значение |
| --- | --- |
| `DEPLOY_SSH_KEY` | приватный SSH-ключ `deployer`; публичный — на сервере в `~deployer/.ssh/authorized_keys` |

Пользователь `deployer` должен иметь права на запись в `DEPLOY_TARGET` и доступ
к docker-сокету (`sudo usermod -aG docker deployer`). После первого успешного
деплоя рекомендуется включить строгую проверку host key
(убрать `StrictHostKeyChecking=no`).

## Хранение (Redis)

- `chat:{id}:messages` + `chat:{id}:msg:{mid}` — лента группы (без прунинга)
- `dm:{userId}:messages` + `dm:{userId}:msg:{mid}` — личка
- `profile:{userId}` — текстовый профиль пользователя

Контекст по токен-бюджету: окно модели берётся из
`GET /api/v1/models` OpenRouter (при недоступности — `fallbackContextTokens`),
оценка токенов — эвристика (кириллица ~2 символа/токен, остальное ~4),
плюс резерв `safetyMarginPercent`.
